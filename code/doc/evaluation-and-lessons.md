# 评测与失败经验

更新：2026-10-17。当前结果、历史对照和失败经验集中在本页；[流程](processing-flow.md)只维护架构，[数据约定](data-contract.md)只维护契约，[TODO](../README.md)只列当前待办。原模型回答、失败日志、哈希和旧实验目录全部保留，不用合并文档覆盖历史证据。

## 1. 验收口径

**识别大类即可通过认物验收，并在动作/实物证据成立后入库。** 饮品、零食、未知食品均可；品牌、口味、200ml等规格是可选增强，不再列作基本失败条件。不能把“没认出东方树叶”解释为饮品认物失败。

| 维度 | 通过要求 | 不影响该维度通过的情况 |
| --- | --- | --- |
| 基本认物 | 目标可辨、不是背景，能给粗类别 | 缺品牌、款式、容量、SKU |
| 库存 | 单件/实例归属和取放证据成立，实际事务有回执 | 名称暂粗；日期/提醒尚待补 |
| 过程历史 | 事件对象与顺序正确；另看最终净变化 | 时间窗较宽须如实说明；品牌不参与评分 |
| 语音事实 | 语义与关键日期/数值正确，保留原话和来源 | 无法确定年份就保存月日候选，不阻止收纳 |
| 日程 | 缺输入保存同一草稿；完整时持久化并按时触发 | 草稿不等于已设置，入队不等于已收到/播放 |

命名粗不等于实例可以混淆。把软糖和鸡胸肉当同件、正背面拆成两件、漏掉放入，仍是错误。模型high与consistent均非正确率；程序测试数量也不等于视频成功数量。

## 3. v7退化的逐模块证据

### 历史确实通过过

`state-actions-v8/v7`的动作顺序为：取出辣条→放入软糖→取出鸡胸肉→放回辣条；净变化软糖add、鸡胸肉remove、辣条kept，pending=0。**该轮通过的是历史/净变化检查，当时未写库存**，也没把ans.md允许提供的初始库存输入模型。旧回答存在outside/absent用词不严谨，不能把通过理解成全部语义完美。

本轮执行`scripts.workflow_review v7`：旧观察交给当前reconcile仍通过，证明当前状态机没有必然破坏v7。旧/新crop的8份图像字节完全相同，evidence、SIFT匹配记录、coverage窗口相同；action-media只有version字段不同，共同帧时间和图像字节相同。主要退化发生在重新调用模型得到的**快照/窗口观察**，并叠加一个确定的复核时间契约缺口。

### 具体错误在哪里

| 环节 | 对照答案与原图的证据 | 影响 |
| --- | --- | --- |
| 解码/候选/crop/窗口覆盖 | 原帧/时间、8份crop及窗口相同；candidate仍obj01鸡胸肉、obj02辣条、obj03软糖 | 这轮退化不是视频漏解码或重新裁错物品引起 |
| 场景规划/ROI | 新旧都覆盖0–4997ms且四个固定窗口相同，但ROI和提示/时序输入一起改变 | 不能单独断言某个ROI或“更多帧”导致退化，需单变量模型对照 |
| c1复核的软糖 | 原观察unknown→unknown；复核误称0ms软糖已在柜内，后变absent，但identity=uncertain | 产生虚假变化pending；不是真实软糖remove |
| c2普通观察的before | 0.966秒原图无软糖，约2.032秒已放入；模型选2.032秒作before、2.765秒作after，两边inside | 省略进入过程，漏软糖add；现行校验只检查顺序，未要求before对应交互前 |
| c2复核/仲裁 | 复核before改用更早0.966–1.233秒；review_conflicts只比before标签的presence，忽略时刻不同 | 合理的“更早未在→后来已在”被当相反观察。另有同一2.765秒放稳状态相反，后者是真实分歧，不能一起取消保护 |
| c3鸡胸肉 | 新观察inside→outside，符合取出 | 这一环节没有失败，不应整段推倒重做 |
| c4实例关联 | 末尾实际只有软糖与白色辣条；模型给obj01和obj02都写inside，甚至为obj01虚构“鸡胸肉/CHICKEN BREAST”文字 | 把同一白包装当两个candidate，错误生成鸡胸肉return |
| 独立结束快照 | 新snapshot把obj01写inside；旧snapshot判不在 | 净变化也错成鸡胸肉kept；只修c4历史还不能修净变化 |
| SIFT提示 | 末帧obj01错误绿框与真实obj02辣条/背景重叠；旧版也有同样提示 | 是确定的误导风险，但因新旧匹配相同，不能把模型输出变化全部归因于SIFT |
| 准入/数据库 | CoarseIntake只支持单新增，且当前确有未决错误 | pending阻止误写是正确保护；即使四步正确，仍需已有item映射和混合操作策略才能自动提交 |

| 视频 | 库存 | 语音/关联 | 日期与日程 |
| --- | --- | --- | --- |
| v9 | 仍1件、revision2，基本认物/入库通过 | “这个可乐是今年7月14日生产的保证期一年”；当前link=pending | 精确substring匹配找不到“可乐/罐装汽水”；缺可信年份，期限疑词保留；用户没要求提醒，0任务/0reminders/0deliveries |

v10两条草稿：before_expiry来自原音频，缺明确年份/到期边界/提醒时刻；after_expiry_remove来自用户配置策略，缺年份/到期边界。后者并非ASR额外识别出一句话。两个副本各有2个既有库存通知jobs，不能说它们是新提醒投递任务。真实回执在该目录report.json。

### 联合检查暴露的架构缺口

- `SpeechService.link`用`subject in item文本`，命名变粗就丢关联；应增加有来源的规范类型兼容匹配，并校验同视频、时间、唯一候选/已有物品竞争和视觉冲突。不能只按“这一段新增一件”或同食品大类强绑所有语句。
- `batch_a.main`发现动作已committed就提前return，会跳过后来请求的语音/任务；应按阶段续跑并查询当前状态，复用稳定ID，避免重新做动作。
- `Tasks.draft`已有草稿直接返回，缺失项也固定加入expiry_date等；关联/日期晚到不会自动刷新，必须补同草稿reconcile，不能新建第二条任务掩盖旧任务。
- `normalized_facts`目前一个uncertainties会整体清空生产/到期/期限；应逐字段保留明确事实和疑词，v9年份缺失、保质期疑词分别核验。语音语义允许口语差异，不能用ans.md改写输入。
- `task_worker`已有APScheduler扫描，生产常驻、部署单实例锁、HTTP会话接入与真实投递还缺。WebUI当前仅预览；未收到设备played不能报播出。

统一架构和执行顺序已并入[流程第6节](processing-flow.md#6-库存与日程的联合架构)，数据结构/周期迁移见[数据约定第6节](data-contract.md#6-日程数据与后续迁移)。先接齐以上联系，再扩展每日/每周，避免新建另一套日程队列。

## 6. 下一轮验收

先固定旧观察与本轮错误观察，分别检查端点、复核时间、实例关联及快照，保持每次单变量和同预算；再对同证据进行无SIFT/有提示、固定端点/自由端点的有限真实模型对照。旧观察替换得到正确结果只算诊断，不当新识别成功。

回归必须保住v8开合、v9手持跨窗、v10已有罐/新增鸡胸肉；v7核对四步和净变化，v4核对早期空柜，v6核对正背面去重。混合提交在独立库模拟明确初始item，验证return、历史、数量和重放。语音联合检查覆盖可乐/汽水、粗名称、同段多件、错误指代、日期晚到/改稿、缺年、草稿刷新与重复提交。

留出视频应另录不同包装/光照/连续动作和语音，分别报告认物、实体、动作、事实、任务、送达、延迟和费用；不能只统计pending率下降。无视频/语音留出与可靠边界标注前，不报告泛化率、mAP或毫秒精度。全部开发流程和待实施模块统一引用[流程](processing-flow.md)与[TODO](../README.md)。
