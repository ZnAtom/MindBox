### 先看优先级怎么理解

- **P0：先完成可演示闭环。** 固定摄像头和拍摄协议，允许任意生活物品，但每次只处理少量、清晰、无遮挡的单件动作；不满足质量条件就进入待确认，不强行写库。
- **P1：再接实时展示和已有库存混合操作。** v7 拆成有序子动作，接上因果回放、数据库幂等和最小 WebUI，让每个动作都能及时显示。
- **P2：最后补充复杂场景和识别增强。** 抽屉连续变形、自动分割、联网搜索、复杂遮挡和大规模泛化都不作为黑客松基础闭环的前置条件。

每项都按“因为 → 准备方案 → 简单来说 → 专业来说 → 完成标准”阅读。这里的“专业来说”是模块或算法名称，便于后续查代码和查资料；“完成标准”是实际验收条件，不是口号。

### P0-A：修正“操作前/操作后”的时间判断 [已完成程序改动]

- **因为：** v7 把已经放入软糖后的画面当成了操作前画面，所以漏记软糖；复核时间没有对齐时，还可能把正常变化当成冲突。
- **准备方案：** 程序明确交互开始和结束的时间范围，单独保存物品首次出现时间；复核时按同一帧或相交时间判断，而不是只拿视频末尾的一张图比较。
- **简单来说：** 先搞清楚“物品在动作开始前就在那里”，还是“物品是在这次动作中出现的”，不让动作结束后的照片冒充起始照片。
- **专业来说：** 这是视频事件的端点约束、时间基线建立、`first_seen` 证据和状态机复核规则。
- **完成标准：** v7 能记录软糖；v9 的“手持进入后放稳”仍能记录；v8 拉开或合上抽屉不会凭动作本身产生误取出；v4、v10 原有结果不退化。
- **本次结果：** 已加入计划端点约束、时间方向复核和回归护栏；历史正确观察通过，新模型错误观察仍会 pending，尚未把视觉模型错误伪装成自动成功。

### P0-B：修正“同一个物品被认成两个物品”的问题 [已完成程序改动]

- **因为：** v7 末尾的白色包装被同时认成辣条和鸡胸肉，独立结束快照还把已经取出的鸡胸肉认成仍在抽屉里。
- **准备方案：** 把整帧、候选局部图和跨帧外观提示放在一起比对，先验证实例是否真的是同一件，再决定是否引入分割或连续跟踪。
- **简单来说：** 一张白色包装只能对应一个真实物品；如果照片角度不同，也要确认它是不是同一件，而不是看到相似颜色就新建一个物品。
- **专业来说：** 这是实例级数据关联、跨帧外观匹配和独立快照一致性校验；SIFT 等局部特征只作为提示，不单独决定入库。
- **完成标准：** v7 末帧不再双重计数；v6 正反面不误合并；取出后独立结束快照不会把物品恢复回来；单变量测试通过后再决定是否投入分割/跟踪。
- **本次结果：** 已加入同帧强重叠提示的排他保护和回归测试；不能确认唯一实例时进入 pending，不直接创建第二件库存。

### P0-C：把库存事实和语音日程接成一条可续跑的流程 [已完成程序改动]

- **因为：** v9 已经入库，但语音“可乐”无法和粗名称“罐装汽水”关联；v10 的语音和配置都生成了待补充任务，后续关联或日期到达时还需要刷新同一草稿。
- **准备方案：** 动作提交后保留可续跑的库存与证据；用类型、别名和候选关系做兼容匹配；把名称、日期、提醒时刻分别记录疑点，晚到信息更新原任务而不是重新新增一条。
- **简单来说：** 先把“这是一件饮品”存下来，再慢慢补“它可能是可乐、哪天买的、什么时候提醒”；补充信息失败不应抹掉已经确认的物品。
- **专业来说：** 这是库存事务与任务草稿的关联、字段级不确定性、别名/类型匹配、幂等更新和阶段续跑。
- **完成标准：** v9/v10 联合检查可以重复运行而不重复入库；“可乐”能关联到已有饮品候选；日期或提醒时刻晚到时刷新原草稿；不因品牌或规格缺失阻塞大类入库。
- **本次结果：** v9 已通过“饮品”类别兼容规则关联到“罐装汽水”；先建任务再补关联/日期会刷新同一草稿，重复运行保持幂等；v10 仍如实保留缺年份、边界和提醒时刻。

### P0-D：确定黑客松演示协议和质量门禁

- **因为：** 不做逐视频人工标注时，系统必须用可执行的拍摄约束换取可靠证据；否则模糊、遮挡和多件重叠会把视觉错误误传成库存事实。
- **准备方案：** 摄像头固定，视频边界包住抽屉；每个子动作只操作一件物品，物品从画面外进入、在画面内清晰展示、进入抽屉后停稳；严重模糊、遮挡、多人手或边界不清时只生成 `pending`。
- **简单来说：** 物品可以是任意生活物品，但一次只放一件、展示清楚；看不清就不猜、不入库。
- **专业来说：** 这是开放集描述、输入质量门禁和证据驱动的拒识策略，不是固定类别分类器。
- **完成标准：** 饮料、零食、袋装物品、盒装食品等不同物品都能入库；未知物品也能用“白色袋装物品”等描述作为名称；品牌和规格缺失不阻塞入库。

### P0-E：v7 四动作因果回放（M5-lite）

- **因为：** v7 把四次操作放在同一段上下文中，模型容易混淆前后状态；整段结束后再推理也会重复解释已经发生的动作。
- **准备方案：** 先用帧差/光流和稳定间隔切出四个动作候选，每个候选保留前后重叠上下文；按时间顺序建立父 `capture_session` 和四个子 `operation`，每个子动作都读取上一步的库存台账，确认后才推进下一步。
- **简单来说：** 把“取出辣条、放入软糖、取出鸡胸肉、放回辣条”分别看，做完一步再把结果交给下一步。
- **专业来说：** 这是因果时序分段、父子操作、状态台账、幂等事务和有界回放；分段不确定时保留整个动作窗口并进入 `pending`。
- **完成标准：** v7 净变化为软糖新增、鸡胸肉移除、辣条保留；同一视频重放不重复写库；合屉动作不会单独产生取出事件。

### P0-F：开放集命名和最小入库回执

- **因为：** 物品种类不能限定为少数类别，但模型也不一定能识别品牌或 SKU。
- **准备方案：** 输出“类别 + 可见外观 + 包装形态”的可读名称，例如“绿色瓶装饮品”“白色袋装零食”“未知盒装食品”；视觉、OCR、RAG 和用户修正分别记录来源，后续补全不能覆盖原始描述。
- **简单来说：** 不知道商品名时也要给一个有区别的描述，保证多样物品不会全部变成“未知物品”。
- **专业来说：** 这是开放世界识别、属性化命名、实例身份关联和字段级来源追踪。
- **完成标准：** 每个已确认物品都有非空名称、粗类别、外观描述、时间、抽屉位置、证据帧和置信等级；名称相似不等于实例合并。

### P1：最小实时 WebUI 和视觉反馈

- **因为：** 黑客松演示需要让观众看到系统正在理解动作，而不是等待整段视频结束。
- **准备方案：** 先回放已到达的视频片段模拟在线流，通过 SSE/WebSocket 推送“检测到物品 → 正在放入 → 已停稳入库”的动作卡片；叠加红色轮廓/轨迹和原始 crop，无法确认时显示待确认原因。
- **完成标准：** v7 四个子动作按顺序出现；每个动作最多一次确认；结束对账只校验，不重新提交净变化。

### P1：已有库存、语音和提醒的联合演示

- **因为：** 现有 v9/v10 已有库存与语音日程基础，可以成为比单纯识图更完整的展示闭环。
- **准备方案：** 动作确认后立即显示粗名称；语音中的日期、保质期和提醒意图异步关联同一 item；缺年份或提醒时刻时保留同一待补草稿，不阻塞库存。
- **完成标准：** v9/v10 联合检查继续幂等；展示“已入库”和“提醒待补”两个独立状态。

### P1：一次性设备配置和可重复运行环境

- **因为：** 不做逐帧人工标注，但仍需要让系统知道抽屉的大致区域和视频协议。
- **准备方案：** 首次运行只配置一次摄像头、视频边界和抽屉四角；后续视频复用配置。同步固定 Python/Docker 启动方式、K230 音视频格式和学校接口模型 ID。
- **完成标准：** 换一段任意清晰物品视频仍能运行；配置丢失或媒体协议不符时明确报错，不猜模型名重试。

### P2：按需补全、联网搜索和复杂视觉

- **因为：** 品牌、容量、条码和网页资料不能稳定从单段视频获得，不应阻塞基本收纳。
- **准备方案：** 先入库粗描述，再按预算调用 OCR/条码、本地 RAG、补拍正面和联网搜索；SAM 2.1、Grounding DINO、动态多边形和遮挡恢复作为独立实验。
- **完成标准：** 补全失败不改变已确认库存；所有外部资料保留来源和时间；复杂遮挡只报告能力边界，不伪称已解决。

### P2：分层回归和留出评测（M7）

- **因为：** 演示协议通过不代表系统适用于任意拍摄条件。
- **准备方案：** 将视频分为演示集、轻度变化集和困难集，分别评估大类、实例、动作、日程、延迟和成本；每次只改变一个模型或算法变量。
- **完成标准：** 演示集稳定通过；其他集合明确记录失败类型，不用 pending 下降代替准确率提升。

P0-A/B/C 已完成程序改动和隔离回归。当前黑客松主线是 P0-D/E/F：用开放集描述覆盖多样物品，用质量门禁控制可识别条件，用四动作因果回放解决 v7 的上下文混淆，再用最小 WebUI 做可见反馈。人工逐帧标注、动态连续轮廓和复杂联网增强不再阻塞首个可演示版本。
