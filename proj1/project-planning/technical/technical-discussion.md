# Mind Box：技术讨论与候选方案

更新：2026-10-13。本文是待你审阅的技术草案，没有开始编码、接线或实测。产品体验见 [产品形态](../product-design/product-concept.md)，已有硬件见 [已确认信息](technical-solution.md)。

## 1. 讨论规则

我提供候选方案、依据、推荐与不确定点，最终由你决定。未经你确认，不移入技术方案。可以先确认某方向用于验证；“用户确认”和“实测通过”是不同状态。

选择时按以下因素判断，不用尚未测过的速度或准确率代替证据：

| 因素 | 要判断什么 |
| --- | --- |
| 能否实现 | 板型、接口、驱动、API 是否支持真实需要的功能 |
| 时间与难度 | 48 小时内能否打通并稳定演示，失败后是否有退路 |
| 熟悉程度 | 你已做过什么、现有代码能否复用；陌生方案的调试成本 |
| 开源复用 | 有无官方例程/成熟实现，兼容性、许可证、部署条件是否合适 |
| 基础效果 | 识别、库存变更、端到端延迟、稳定性与纠错负担 |
| 成本与约束 | 采购到货、网络、功耗、续航、隐私与维护成本 |

当前优先参考你做过的 K230 画面传电脑经验。资料入口只是复用线索；本轮未完成联网版本核对，也未在你的板卡上验证。

## 2. 数据在哪里处理

| 候选 | 分工 | 优点 | 主要代价 |
| --- | --- | --- | --- |
| A：电脑集中管理，优先推荐验证 | K230 提供图像；电脑做识别/调用 API、库存、提醒与 Web UI；ESP32 按需做传感器和录播 | 可复用画面传输经验，调试与存储方便，减少嵌入式移植 | 需要电脑运行，须验证设备到电脑的通信 |
| B：K230 主控 | K230 做本地视觉、记录与网络请求，ESP32 按需处理音频/传感器 | 产品更独立 | 板型/固件能力、模型转换、存储与 Web 服务适配成本待查；不假设能本地运行通用大模型 |
| C：远程服务器集中管理 | 设备上传图像/事件，服务器管理库存与提醒；屏幕浏览远程 Web UI | 展示时可不使用本地电脑作后端 | 依赖外网、服务器部署和重连处理，须实测延迟 |

**建议：先评估 A。** 电池供电与后端在哪里运行分别决定：无线、电池不代表设备自行完成所有计算。

供电先建议按开发板规格用稳定有线电源，测整机峰值/平均功耗后再讨论电池、稳压与续航。续航应由电池可用能量、转换效率和平均功率估算，再实测；不凭电池容量直接承诺小时数。

图像优先沿用你已有的传输链路。WiFi 适合图像与事件，但需确认 K230 板卡/模块及 SDK 支持；蓝牙优先作为小消息候选，不优先承担视频。具体协议尚未决定。

## 3. 候选 A 的设备分工与通信

以下为推荐草案，不是已确认接线。

| 部分 | 推荐职责 | 通信候选与待查 |
| --- | --- | --- |
| K230 | 摄像头采集，提供前后画面/稳定快照；是否运行本地检测再评估 | 原有视频链路可作取帧源；也可上传 JPEG。帧需带设备、序号、区域与时间信息 |
| ESP32（可选） | 读门磁与 HX711；若录播例程可用，再承担麦克风/扬声器 | 调试可用 USB 串口 JSON，无线可用 HTTP/持续连接。GPIO、电压、音频接口和引脚冲突需核对 |
| 电脑后端 | 统一库存事实、图像识别、语音处理、数据库、任务调度 | 图像/传感器上传走 HTTP 或已有链路；状态推送候选 WebSocket；库存变化必须由后端校验与写入 |
| 屏幕/浏览器 | Web UI 显示库存、照片与提醒 | 访问电脑局域网服务；后端与屏幕不必是同一设备，屏幕硬件尚未提供 |

门磁/HX711 也可接 K230，但要比较现有例程和空闲引脚后决定。先打通一个收纳区域，不因有 3 门磁、2 称重而同时做全部区域。

候选流程：门开/重量变化记录事件，取前后图像；手离开、重量/画面稳定后识别变化；后端校验后更新库存并推送屏幕。关门后看不到物品的形态，应在关闭前保留有效画面，不能假设每次关门后都能拍到。触发、去抖与稳定等待时长需实测。

重量辅助判断变化与稳定，不单独决定是哪件物品或精确数量。安装时托盘载荷必须传给传感器，导柱等支撑不能绕过称重受力路径；先做空载和已知重量标定。

消息使用唯一事件 ID 去重，保存原始事件再分析。设备时钟未同步时同时保存接收时间，不能伪造精确入库时刻；结果按事件顺序处理，旧识别结果不能覆盖较新的状态。断网重传、失败可重试，不重复入库。

电脑可在接收门磁/重量事件后建立采集会话，让快照和识别结果携带同一会话 ID，便于关联不同设备的数据。实时流的缓存延迟和前后帧选择仍要实测，不能把消息到达顺序直接当作物理动作顺序。

校园网可能有客户端隔离，演示前要验证设备、后端和屏幕互相可达；热点或路由器局域网为候选备用。

### 语音候选

- 先用电脑麦克风/扬声器跑通查询与一次性提醒，再接 ESP32 音频，是调试退路；最终交互由你决定。
- 若 ESP32 的现成录播例程可用，可采集音频传给电脑，电脑调用 ASR/理解意图，生成语音后让板卡播放。板上有音频硬件不代表当前固件与格式已经可用。
- 自然唤醒、连续监听、回声消除为额外成本；输入入口尚未定案。语音服务可选不等于用户必须说话才能入库。
- 定时任务落在后端持久化与调度，不靠大模型一直“记着等 3 分钟”。时钟到期后推送屏幕/播放提醒，重启不能丢任务。

## 4. 摄像头与采购建议

| 项目 | 当前建议 |
| --- | --- |
| 第一个可用摄像头 | 先确认 K230 当前摄像头、接口、镜头和视野；若缺失，优先采购已知兼容板型/固件的模块 |
| 第二摄像头 | 暂不作为必买；先测单视角覆盖。若侧面盲区明显且影响核心功能，再考虑增加 |
| 第二视角的接入 | 电脑方案可考虑 USB 摄像头直接接电脑；K230 双摄支持不能只凭芯片名称判断，要核对板卡接口与驱动 |
| 补光与安装 | 优先检查光线、反光、固定支架与视野；必要时补灯，比盲目增加摄像头更直接 |
| 麦克风/扬声器 | 已有 ESP32 音频，先查例程，不默认再买一套；电脑录播可作验证退路 |
| 称重组件 | 已有传感器、711 模块与机械件，先核对数量、标定和接线，不先重复购买 |
| 电池与供电 | 先确定板卡供电规格与功耗；再买匹配的电池/电源方案 |

待补信息：两块开发板准确型号、现有摄像头和固件、711 模块数量与型号、ESP32 音频芯片/例程、屏幕方案、电脑配置与可用 API 模型。未核对前不列具体购买型号。

多摄像头会增加视角对应、同步、去重和模型输入成本，是否增购按实际覆盖缺口决定，不默认数量越多效果越好。

## 5. 数据模型草案 v0

**建议电脑后端以 SQLite 和图片文件存储作为候选起点。** 不是最终数据库决定。四张核心表：物品、事件、观察、提醒；首个区域可用配置，后续再增加区域表。

一行物品优先代表一件或一包装，同款不同放入时间不合并。无法区分同款个体时，必须说明数量/身份不确定，不直接假装完整追踪。

### 5.1 物品 `items`

| 字段 | 用途与获取方式 |
| --- | --- |
| `item_id` | 后端唯一标识，名称不是主键 |
| `location_id` | 所属收纳区域，首版可只有一个 |
| `name`、`category` | 视觉识别或用户主动补充；未知名称可显示照片。分类候选：水果、零食、饮料、保健品、药品、其他、未知 |
| `quantity`、`unit` | 有依据时保存；不确定为 NULL，不把重量直接换成件数 |
| `stored_at` | 直接观察到或有依据推测的入库时间，通过元数据区分；未知为 NULL |
| `first_seen_at`、`last_seen_at` | 首次、最近一次实际观察时间，不能被时间回推覆盖 |
| `presence_status` | `present` / `unseen` / `removed` / `uncertain`；未见不自动删除 |
| `production_date`、`shelf_life_days` | 可选；包装信息明确或用户主动提供时记录，不要求填写 |
| `expires_at` | 实际包装日期，或由明确生产日期与保质期计算；未知为 NULL |
| `opened_at` | 可选开封时间；无法观察/确认时未知 |
| `review_at`、`review_reason` | 建议关注时刻和理由，不能作为真实到期日 |
| `latest_observation_id` | 关联最近观察与照片，历史仍保留 |
| `notes` | 用户主动补充，可为空 |
| `field_meta` | 关键字段的来源、确定程度和证据；无需给主键/系统更新时间重复套状态 |
| `created_at`、`updated_at` | 后端记录维护时间，不当作物品入库时间 |

遮挡回推加分项可另加 `stored_from`、`stored_to` 与候选入库事件关联。多候选时保留范围，不能填一个看似精确的时间。

### 5.2 字段依据与界面

业务值存正常列；关键字段的 `field_meta` 保存以下信息，不把全部字段包装成复杂对象：

| 属性 | 候选定义 |
| --- | --- |
| `source` | `vision` / `label` / `user` / `web` / `system`；未知可为空 |
| `certainty` | `recorded` 有直接记录 / `estimated` 推断 / `unknown` 未知；有记录不代表绝对无误 |
| `evidence_refs` | 可选：原始照片、事件或用户指令 ID；网络信息保存链接与查询时间 |

网络商品通常保质期不能证明这件物品何时生产或到期。估计不自动覆盖包装或用户给出的不同信息；冲突保留证据并标明待核实。模型自报置信度不当成真实准确率。

由日期和时长计算出的字段须继承输入的不确定性，估计输入不能产生“确定”的到期日。模型提供候选识别/提取和工具意图，后端校验字段、日期与物品关联后写入；系统时间和原始传感器数据不由模型编造。

界面默认展示照片、名称、分类、位置、存放时长、已知日期和下一提醒；数量有依据才显示。必要时用“约”“日期未知”“最近未看见”，来源细节按需展开。后台字段不全部变成表单，不因缺失强制追问。

### 5.3 事件 `events` 与观察 `observations`

| 表 | 候选字段 |
| --- | --- |
| `events` | `event_id`、`device_id`、`boot_id`、`sequence_no`、`capture_session_id`（可空）、`location_id`、`kind`、`device_time`、`received_at`、`payload`、`processing_status` |
| `observations` | `observation_id`、`event_id`（可空）、`captured_at`、`received_at`、`image_ref`、`visibility_status`、`recognition_result` |

事件类型候选：门开/关、重量变化、稳定画面、用户指令。载荷可保留原始重量、门状态、设备版本。图像保存文件，数据库保留路径；识别结果关联观察中的物品、位置和依据，可保留未识别区域，不虚构遮挡物品。

`event_id` 和“设备 + 启动标识 + 序号”用于重传去重，避免设备重启后序号归零造成误去重；所有时间统一存 UTC，用户界面按上海时区显示。原始设备时间与后端接收时间同时保留；提醒调度使用后端时钟。

关联记录应能表达“一个物品有多次观察、一次观察有多个物品”，具体采用关联表或结构化结果待实现选型。不依赖最新一张照片重建全部库存。

### 5.4 提醒 `reminders`

| 字段 | 用途 |
| --- | --- |
| `reminder_id` | 唯一任务 ID |
| `item_id`、`target_text` | 物品关联或通用目标；“提醒吃苹果”若无法唯一定位，不创建虚假物品 |
| `origin` | `user` 主动指令 / `rule` 系统规则；后者规则与默认开关仍待讨论 |
| `message`、`due_at` | 内容与实际触发时间，不能只存“三分钟后”文本 |
| `repeat_rule` | 首版可空，重复提醒为可选扩展 |
| `status` | `pending` / `triggered` / `canceled`，触发不等于用户已执行 |
| `created_at`、`triggered_at`、`last_delivered_at` | 任务记录、调度与输出时间，分别测量 |

语音意图经过后端校验再创建任务；一次性任务持久化，重启后检查待到期任务。接收与播放确认要避免重复提醒，不能把响过当作吃过。“3 分钟”建议从指令被接受时计算并显示预计时刻，语音传输延迟另测。

## 6. AI 选择与基础效果怎么保证

| 路线 | 适合什么 | 主要风险 |
| --- | --- | --- |
| 云端多模态模型，优先候选 | 识别多样食品/包装，避免赛时训练；稳定快照按需调用 | 网络、API 延迟、误识别和结构化输出；具体可用模型待你提供 |
| 电脑本地检测 + 云端理解 | 本地找物品/判断变化，云端命名和理解指令 | 要核对模型支持的类别；额外模型不一定让整体更快 |
| K230 本地检测 + 后端理解 | 边缘检测、限制类别，减少部分传输 | 模型适配、转换、量化与板卡例程成本；端侧速度不能代替整条链路速度 |

不先承诺准确率或秒数。优先用现有 API 做有限物品集、稳定快照的验证；局部裁剪可以减小输入，但包装文字不能被压得无法读取。避免连续上传每帧到大模型，预览流与识别快照分开。

**验证清单：**

- [ ] 核对板卡、摄像头、GPIO、音频与原有代码，打通采集和消息。
- [ ] 测目标零食、水果、饮料的单件及小批量，记录正确名称、数量、进出判断与未知结果。
- [ ] 测手部经过、空操作、光照变化、重复上传、拿出放回，统计重复入库与错删；严重遮挡单列加分项，不混进基础承诺。
- [ ] 分段记录拍摄/稳定等待、传输、模型、写库、屏幕更新时间，以及整段 P50/P95 延迟。
- [ ] 比较少量现有可用模型的准确性、P95、成本和失败情况，再由你选；没有实测结果不宣布最佳模型。
- [ ] 测持续运行、网络中断、设备/后端重启；库存能恢复，提醒不丢失，输出不重复。

候选 Demo 目标（供确认，不是性能结果）：有限物品集做 30 次代表性操作，正确库存变更至少 27 次，重复入库/无依据错删目标为 0；稳定画面后到屏幕更新 P95 不超过 5 秒；提醒后端触发偏差目标不超过 1 秒。未识别、错误与降级分别记账，不能删掉失败样本。音频播放延迟与采集等待另计入用户实际体验，必要时调整范围。

如果不达标，优先改善光照/视野、收窄物品种类和批量规模，再比较模型或增加摄像头。算法、镜头或硬件调整后重新测相关项，不能把目标值当成保证。

## 7. 复用线索与待决定事项

以下为候选资料入口，未下载、未核对当前版本和板卡兼容性：

- [K230 CanMV](https://github.com/kendryte/k230_canmv)、[K230 SDK](https://github.com/kendryte/k230_sdk)：先找匹配固件的摄像头、网络、GPIO 与推理例程；最优先检查你已有电赛代码。
- [ESP-ADF](https://github.com/espressif/esp-adf)、[ESP-Skainet](https://github.com/espressif/esp-skainet)：音频/语音候选，不代表你的 ESP32 板型可直接使用。
- [OpenCV](https://github.com/opencv/opencv)、[Ultralytics](https://github.com/ultralytics/ultralytics)：电脑图像变化和检测候选，检查类别、依赖与许可证。
- [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)：离线语音候选，需核对中文模型、资源消耗与部署成本；也可比较已有云端语音 API。

下一轮优先决定：是否先验证电脑主控 A；K230 与 ESP32 如何分工；沿用何种画面传输；哪些字段首版必要、如何展示；基础验收目标是否合理。你确认后再将相应决定移入 [技术方案](technical-solution.md)。
